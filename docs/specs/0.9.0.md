# Spec: tix 0.9.0 - statuses from the config, parent and child tasks

Status: the model (sections 2.1, 3.1, 6) is accepted by the user on 2026-11-12; section 8 lists what waits for the user.
Parent: `docs/spec.md`. Replaces `docs/spec.md` 2.5 "five fixed statuses" and D69; replaces the epic as a tagged task with a list.
Research (2026-11-12): Linear and Plane bind behavior to a status type or group, never to the name; Plane
refuses to delete a status that has tasks; Linear, Plane and Backlog.md store the parent in one field of
the child. Backlog.md has a flat status list where "closed" is the last status, and its board and
statistics still match the word `Done`.

## 1. Goal and boundaries

- Goal: the functional base for the 0.10.0 interface. Statuses are configured, an epic is linked to its
  tasks as a parent to its children, and every action is a core operation.
- We do: statuses with a kind in `.tix/config.toml`; add, rename, remove a status; the field `parent`;
  children and progress computed by tix; migration of the old epics; unchecking a criterion; the TUI keeps
  working.
- We do not do: any new interface (web, new TUI screens, sort and filter - 0.10.0); status colors;
  reordering statuses by command; nesting deeper than one level; automatic closing of a parent or of
  children; several parents; a handoff status with its own claim rules.

User decisions, 2026-11-12:

- A status is a name plus a kind. Statuses can be added, removed and renamed.
- An epic and a ticket are linked as a task and a subtask. An epic is any task that has children.
- The 0.10.0 interface must be buildable with no change in the core.

## 2. Statuses

### 2.1 Model

- A status has a name and a kind. The kinds are fixed: `idea`, `open`, `in_progress`, `blocked`, `closed`.
- Every rule of the core reads the kind, never the name. All statuses of one kind behave the same.
- An agent or a human types the name only. The kind is typed in one place: when a status is added.
- The statuses live in `.tix/config.toml` as an ordered list. The order of the list is the board order.

```toml
format = 2

[[status]]
name = "idea"
kind = "idea"

[[status]]
name = "open"
kind = "open"

[[status]]
name = "in_progress"
kind = "in_progress"

[[status]]
name = "review"
kind = "in_progress"

[[status]]
name = "blocked"
kind = "blocked"

[[status]]
name = "closed"
kind = "closed"
```

- A config with no `[[status]]` section means the five default statuses, each named as its kind. A store
  of 0.8 behaves as before.
- A name is `[a-z0-9_]+`, up to 20 characters, unique. A name equal to a kind word is allowed only for a
  status of that kind (`closed` with the kind `open` is refused), in the config and in every operation.
- A config is valid when every kind has at least one status. An invalid config is an error with the file
  and the line; the core does not write.
- The first status of a kind in the list is the default of the kind.
- Why this is not D24 again: D24 had one role per column, so every column had two equal names and agents
  mixed them. Here a kind has any number of statuses, the kind is never typed in a task command, and text
  output shows it next to a name that differs from it (2.2).
- The core reads `config.toml` under the store lock at the start of every write operation, so a
  long-lived process (the TUI, the future web server) never checks a move against a stale list. The TUI
  reloads the config on every board refresh.

### 2.2 Rules by kind

The table restates `docs/spec.md` 2.5 with kinds. With the default config no reply and no refusal changes.

| Operation | Rule |
| --- | --- |
| `new` | without `--to` the task goes to the default status of the kind `idea`; `--to NAME` takes a status name; the entry checks follow the kind of NAME |
| `move NAME` | NAME is a status name; the checks follow the kind of NAME and the kind of the current status; a move between two statuses of one kind has no checks and keeps the claim, the waiting reason and the result |
| `take` | allowed from the kinds `open`, `blocked`, `in_progress`, and from `idea` when the task has criteria (as today); a task of the kind `in_progress` stays in its status; otherwise it goes to the default status of the kind `in_progress` |
| `take --release`, session end | a task of the kind `in_progress`, whatever its status, goes to the default status of the kind `open` |
| `done` | a task not of the kind `closed` goes to the default status of the kind `closed`; a task already of the kind `closed` stays where it is, the reply is `ok` with no commit (as today) |
| `list --status NAME` | filters by status name; `list --kind KIND` filters by kind |
| `ctx`, `list` | group by kind in config order of the statuses, then by rank |
| `After:` and stale checks | "closed" means the kind `closed` |

- Text output (`list`, `ctx`, `show`, the replies of `move` and `take`) prints a status as its name when
  the name is the kind word, and as `name [kind]` otherwise: `review [in_progress]`.
- `list --json` and `ctx --json` have `status` and `kind`.
- A status name that is not in the config: the refusal lists the configured names. The old-word hint
  (`todo`: "maybe open?") is given only for a word that is not a configured name.
- A task file with a status that is not in the config (a hand edit, an interrupted rename): `list` and the
  board show it in the column `?`; `move` to a configured status is allowed with the checks of the target
  kind and clears the claim.

### 2.3 Status operations

Core operations, each under the store lock and in one commit. The CLI calls them and prints the reply.

| CLI | Core | Behavior |
| --- | --- | --- |
| `tix status` | `Statuses` | prints the list in board order: name, kind, number of tasks |
| `tix status add NAME --kind KIND` | `AddStatus` | adds a status after the last status of its kind; it never becomes the default of the kind |
| `tix status rename OLD NEW` | `RenameStatus` | rewrites `status:` in every task of OLD, then renames the status in the config |
| `tix status rm NAME` | `RemoveStatus` | removes a status with no tasks |

- Refusals of `add`: the name exists, the name is malformed, the name is a kind word of another kind, the
  kind is unknown.
- Refusals of `rename`: OLD is unknown, NEW exists or is malformed, NEW is a kind word of another kind.
- Refusals of `rm`: the status has tasks (the reply names the count and the hints `tix status rename` and
  `tix move`); the status is the last one of its kind.
- `rename` and `rm` refuse when a task file does not parse, and list the files: tix cannot tell their status.
- `rename` writes the task files first and the config last, reusing the file rewrite of the old column
  migration (the raw `status:` line only; claims and other fields are untouched). An interrupted rename
  leaves some tasks in NEW, which is not in the config yet (column `?`); running the same command again
  finishes it.
- The first status operation on a config with no `[[status]]` section writes the five default statuses
  first. Hand-written comments and key order of `config.toml` are not kept, as with `[paths]` today.

## 3. Parent and children

### 3.1 Model

- A task has an optional front matter field `parent: T-N`. It is the only place where the link is stored.
- A task has at most one parent. The depth is one: a task with a parent has no children, a task with
  children has no parent.
- An epic is a task that has at least one child. There is no epic type and the tag `epic` has no meaning.
- The children of a task and its progress are computed in one pass over the task list: the tasks whose
  `parent` is this task; progress is the children of the kind `closed` out of all children.
- The children are printed in the order of their numbers.
- Hand edits: tix prints the link as written, never follows it deeper than one step and never fails on it.
  A `parent` that points to a missing task prints `Parent: T-N (not found)`. A state that `set` would
  refuse (a parent that has a parent, a link to itself) is shown as written; the next `set parent=` on
  that task applies the refusals.

### 3.2 Operations

| CLI | Core | Behavior |
| --- | --- | --- |
| `tix new "title" --parent T-N` | `CreateWithBody` with a parent | creates a child |
| `tix set T-5 parent=T-N` | `Set` | sets or changes the parent |
| `tix set T-5 parent=` | `Set` | clears the parent |
| `tix show T-N` | `Show`, `Children` | a child prints `Parent: T-N`; a parent prints `Children: 3/7` and a line per child: status, number, title |
| `tix list`, `tix ctx` | | a parent is marked `[epic 3/7]`; `list --json` has `parent` and, for a parent, `children` and `children_closed`; `ctx --json` keeps `epic: true` |

Refusals of setting a parent:

- the parent does not exist; the parent is the task itself;
- the parent has a parent (depth one);
- the task has children (depth one);
- the parent is of the kind `closed` (a closed epic takes no new work; reopen it first).

### 3.3 Rules

- Closing a parent with a child that is not of the kind `closed` is refused, `--force` included. The reply
  names the open children.
- Closing the last open child prints `epic T-N: all tasks closed, ready for acceptance`. The parent is
  not closed by tix: the user accepts it.
- Moving a child out of the kind `closed` while its parent is of the kind `closed` is allowed and prints
  `warning: parent T-N is closed` (today the epic line is unticked and the epic stays closed). So a closed
  parent can have an open child only through a reopened child or the migration.
- Removing a task that has children is refused; the reply says to clear or move the children first.
- `list --like` leaves parents out, as it leaves epics out today.
- The acceptance criteria of an epic are the ordinary criteria in its `## Details`.

## 4. Migration of the old epics

- The sign: `config.toml` has no `format = 2`. A store with the sign is migrated when it is opened by
  0.9.0 for a write, under the lock, in one commit `migrate: epic lines to parent` that also writes
  `format = 2`. A store with `format = 2` is never scanned again.
- Undo: `git revert` of that commit in the store, together with going back to the 0.8 binary. 0.9 migrates
  a reverted store again on its next write.

The rules are evaluated on a snapshot of all task files read before the first write; a file written by an
interrupted run counts as it is on disk. For every criterion line `- [ ] T-N <gist>` or `- [x] T-N <gist>`
of a task with the tag `epic`:

1. The parent of T-N is chosen first: among the tagged epics that list T-N, the one with the largest
   number. If T-N already has `parent` equal to one of the epics that list it, that epic stays the parent.
2. The link is made when T-N exists, has no task lines of its own, has no children, and has no `parent`
   or has `parent` equal to the chosen epic: T-N gets `parent: <chosen epic>`. The line of T-N is removed
   from every epic that lists it. The status of the epic, the mark of the line and the claim of T-N do
   not matter and are not changed.
3. Otherwise (T-N does not exist, is itself a tagged epic with task lines, has children, or has a
   `parent` that is none of the epics that list it) the line stays as an ordinary criterion in every epic.

- After the lines are processed the tag `epic` is removed from the task.
- Write order: the children first, each epic once (lines and tag), `config.toml` last. A run interrupted
  before the config is written repeats on the next write and reaches the same result.
- The migration prints one line to stderr: the number of epics and of children, the tasks listed in
  several epics and the tasks of rule 3 by number.
- After the migration a `- [ ] T-N` line in a body is an ordinary criterion. The writers of such lines
  (the skills `spec` and `orchestrate`, `RULES.md`) are updated before 0.9.0 is installed (section 9).

Counts that must hold: children = distinct T-N of rule 2; removed lines = children plus their extra
occurrences in other epics; kept lines = the lines of rule 3.

A build of `main` between slices 8 and 11 is never run on the real store: it would migrate the store
before the rules of 3.3 and the writers of epic lines are ready. Until the release it runs on copies only.

## 5. Criteria: uncheck

- `tix uncheck T-12 2 3` clears the mark of criteria 2 and 3. Core operation `Uncheck`.
- Refusals: the number is out of range; the task is of the kind `closed` (reopen it first).

## 6. Core first

- Every behavior of sections 2-5 is a public operation of `internal/core` with its refusals inside. The
  CLI parses arguments and prints the reply; it holds no rule.
- The TUI and the future web interface call the same operations.
- Mechanical check: a test fails when a non-test Go file outside `internal/config` and `internal/core`
  compares the status of a task itself (`.Status ==`, `.Status !=`, a `switch` on `.Status`). Such code
  asks the config for the kind and compares the kind with a kind constant. Reads of a long-lived process
  take the config that the last board refresh loaded.

## 7. TUI

Repair only, no new screens.

- The board columns are the statuses of the config, in config order, plus `?` when needed.
- Grab, move and new work with any configured status; the confirmations (`blocked` reason, close result)
  follow the kind.
- The card line of a parent shows `EPIC 3/7` from its children.
- The key `del` on a parent shows the refusal of 3.3.
